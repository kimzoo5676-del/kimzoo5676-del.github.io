배경 & 문제

예·적금 상품을 추천받을 때, 최고 금리순으로는 조회할 수 있었지만 내가 결국 얼마를 수령하는지는 직관적으로 알 수 없었습니다. 그래서 최고 금리만 보여주는 것이 아니라 사용자가 최종적으로 받게 되는 금액을 같이 보여주고, 상품 속 어려운 금융 용어는 쉬운 말 풀이와 AI 챗봇으로 설명하는 서비스를 만들었습니다.

2인 팀에서 백엔드·인프라·AI를 전담해, 데이터 수집부터 추천 로직, LLM 연동, 배포까지 맡았습니다.

시스템 아키텍처

프론트는 Vercel에, 백엔드는 AWS EC2에 나눠 올렸습니다. EC2에서는 nginx가 HTTPS를 받아 Django로 넘기고, Django는 gunicorn으로 돌리면서 서버가 켜질 때 자동 실행되게 등록해뒀습니다. 상품이 766건이고 서버가 한 대라 DB는 SQLite로 정했습니다.

서버에 접속해 하던 배포를 Actions로

수동 배포를 EC2 self-hosted 러너로실패하면 직전 커밋으로
상황서버에 접속해 코드를 받고 재시작하는 수동 배포였습니다
해결EC2 안에 GitHub Actions 러너를 설치해 서버가 직접 배포하게 했습니다 — 코드 동기화 → 마이그레이션 → gunicorn 재시작 → 헬스 체크 5회, 실패하면 직전 커밋으로 되돌리고 재시작합니다
판단GitHub에 서버 접속 키를 두지 않아도 되는 대신, 빌드가 서비스와 같은 서버 자원을 씁니다
결과발표 주에는 버튼을 눌러 배포했고, 안정된 뒤 develop push 자동 배포로 바꿨습니다

우대조건 정합성과 추천

정규식이 '없음'까지 우대조건으로 잡음338 → 115개
상황금융감독원 우대조건(spcl_cnd)은 은행마다 형식 없이 쓴 자유 텍스트라, 처음에는 줄마다 정규식으로 조건과 금리를 뽑았습니다
원인「없음」 · 「해당없음」 · 머리말 줄까지 조건으로 잡혀 적금 338개가 모두 「우대조건 있음」이 됐고, 추천 필터가 의미 없이 동작했습니다
해결우대율(%)이 적힌 줄만 조건으로 인정해 실제 우대율이 있는 115개만 「있음」으로 바로잡았습니다
다음중복 적용이 안 되는 조건과 「고시금리 포함」 표기 때문에 우대금리 합산이 계속 어긋나, 합산을 버리고 금감원 기본 · 최고 금리를 그대로 쓰기로 했습니다
우대조건을 태그로 정형화하는 배치추천 요청 LLM 0회
해결LLM이 상품마다 우대조건 태그 · 연령 제한 · 최소 가입금액을 JSON 하나로 뽑게 했습니다. 태그는 데이터 빈도를 보고 적금 4종 · 예금 4종으로 정했습니다
분리수집 · 태깅 · 요약은 관리 명령(sync_products --with-llm)으로 미리 DB에 저장하고, 추천 API는 저장된 조건 · 태그로만 거릅니다
재처리응답은 JSON으로 강제하고, 실패한 상품은 비워 두어 다시 돌리면 남은 상품만 채웁니다
결과상품 766건 모두 요약 · 태그를 채워 적재했고, 추천 요청 때는 LLM을 부르지 않습니다
세후 실수령액으로 정렬이자에 15.4%
해결이자에만 세율 15.4%를 매기고 적금은 단리 · 월복리 적립식, 예금은 단리 · 월복리로 나눠 계산한 뒤, 상품마다 세후 수령액이 가장 큰 옵션을 대표로 골라 내림차순으로 정렬했습니다
보완태그가 맞는 상품만 남기자 후보가 59개뿐이어서, 우대조건이 없는 상품도 통과시켜 약 228개로 늘리고 단위 테스트를 붙였습니다

챗봇 답을 받는 대로 보여 주기

답이 다 만들어질 때까지 빈 화면조각을 받는 대로
상황LLM 답을 한 번에 받으면 다 만들어질 때까지 사용자는 빈 말풍선만 봅니다
서버GMS를 stream=True로 불러 data: 조각을 [DONE]까지 읽고, StreamingHttpResponse로 받는 대로 흘려보냅니다. nginx가 모아 두지 않게 X-Accel-Buffering: no를 붙였습니다
화면프론트는 fetch 응답을 body.getReader()로 읽고, TextDecoder의 stream 옵션으로 조각 경계에서 한글이 깨지지 않게 했습니다. 받은 글자는 버퍼에 쌓아 setInterval로 몇 글자씩 그립니다
예외질문이 없으면 400, 대화 기록은 프론트가 들고 최근 5턴만 보내며, 실패하면 안내 문구로 바꿉니다
로그인 — 자체 회원 모델에 JWTsimplejwt
해결Django User 대신 자체 Member 모델을 쓰고, simplejwt 인증 클래스가 Member를 조회하도록 맞췄습니다(access 1시간 · refresh 7일)
문서drf-spectacular로 API 문서를 띄우고 JWT Bearer 인증을 표시했습니다

결과 & 배운 점

766개 상품을 세후 실수령액 기준으로 정렬해 주는 서비스를 실제 도메인에 배포했습니다. 기획한 서비스 구현을 위해 우대조건을 구조화해야 해서 정규식으로 파싱하려 했으나, "최대 연 5.0% 우대금리가 적용돼요" 같은 우대조건이 아닌 문구가 조건으로 잡혔습니다. 은행마다 표현이 달라 비슷한 오류가 계속 나왔습니다. LLM 구조화로 바꾼 뒤에도 우대조건이 완벽하게 파싱되지는 않았습니다. 배정된 API 예산을 절반쯤 쓴 시점에 전부 파싱하는 건 포기하고 실제 데이터를 확인하며 보편적인 조건 8개를 표준 태그로 정했습니다. 가정하지 말고 데이터를 확인한다는 원칙을 경험하며 배웠습니다. 그 결과 삼성청년SW·AI아카데미 1학기 관통 프로젝트 최우수상(서울2반 1등)을 받았습니다.
