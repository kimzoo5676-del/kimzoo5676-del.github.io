아키텍처

관리 서버(EC2 · 컨트롤 플레인 · 러너 · 모니터링)까지 구축했고, 워커 노드(SSAFY Lightsail)와 Argo CD 배포는 서버를 받는 대로 붙입니다. 아래는 목표 구성입니다.

CI를 만들기 전에 병목부터 재기

러너 CPU를 잡 갈래별로 나누기backend 잡 136 → 39초
상황여신보좌관은 CPU 4개인 운영 서버에 러너를 함께 두어, 테스트가 쌓이자 MR 파이프라인이 중앙값 약 11분, 기다림 상위 10% 23분까지 늘었습니다. NEW:LEARN 관리 서버는 vCPU 2개를 컨트롤 플레인 · 모니터링과 나눠 씁니다
설계노드 예약 1190m를 빼고 남은 810m에 맞춰 갈래(W0~W4)별 CPU 요청 · 상한을 정했습니다 — backend 잡 550m
측정잡 끝에 cpu.stat을 남겨 backend 잡이 2221 구간 중 2036(92%)에서 상한에 막힌 것을 확인했습니다
해결CPU 4개인 노트북을 두 번째 러너로 붙이고, EC2 러너는 늘 켜진 기본 러너로 두었습니다
결과backend 잡 136초 → 39초, 파이프라인 305초 → 119초
관측을 먼저 올리고, 캐시는 재서 고르기캐시 572초 → 320초
관측추가 요금이 없는 Prometheus · Grafana를 CI보다 먼저 올리고, CPU 상한 0.1 시험 Pod로 스로틀 지표가 잡히는지 확인했습니다(98.7%)
캐시캐시 없이 480~490초, GitLab 기본 캐시는 압축 때문에 오히려 572초 → 캐시 폴더를 직접 쓰는 방식으로 바꿔 320초
결과CI를 21번 돌린 뒤에도 CPU 크레딧 잔액 54 → 269.8 — 지금 서버로 감당합니다

구현과 측정은 Claude Code에 맡기고, 구성과 비용이 걸린 결정은 직접 했습니다. 잰 방법과 함께 기록된 값만 근거로 씁니다.

공부한 IAM 원칙을 Terraform 서버 구축에

콘솔 클릭 대신 코드로 서버 만들기자원 7개 · apply 19초
상황콘솔에서 만든 자원은 무엇이 만들어졌는지 코드로 남지 않아, 다시 만들거나 지울 때 사람 기억에 기댑니다
해결서버 · 보안 그룹 · 고정 IP · 예산 알림을 Terraform으로 정의했습니다. 상태 파일은 S3(버전 관리 · 퍼블릭 차단 · 잠금)에 두고, plan을 읽은 뒤 저장한 plan 파일로만 apply합니다
방어SSH는 관리자 IP /32만 열고 0.0.0.0/0 입력은 변수 검사로 거절하며, 보안 그룹은 테스트로 검사합니다. IMDSv2 필수, 예산 알림 80 · 100% · 예측
결과plan으로 확인한 자원 7개를 그대로 apply했고, 같은 코드로 다시 만들고 지울 수 있습니다
apply 키의 권한을 필요한 만큼으로키가 새도 서울 리전 밖은 불가
상황넓은 권한의 키는 새는 순간 계정 전체가 위험합니다. Zoolog에 정리한 IAM 공부(최소 권한 · Condition 키 · 루트 키 삭제)를 그대로 적용했습니다
해결루트 계정에는 액세스 키를 만들지 않고, plan은 읽기 전용 사용자, apply는 콘솔 접근 없는 전용 사용자로 나눴습니다. 고객 관리형 정책은 EC2 · Budgets · S3(newlearn-tfstate-*만) · STS, EC2에는 aws:RequestedRegion = ap-northeast-2
판단SSO(Identity Center)는 조직을 만들면 무료 크레딧이 사라져 쓰지 않고, 대신 장기 키의 범위를 좁혔습니다
결과다른 리전 조회가 거절되는 것까지 확인 — 키가 새도 서울 리전의 EC2 · 예산 · 상태 버킷 밖은 건드릴 수 없습니다
