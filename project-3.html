배경 & 문제

팀으로 뭔가를 준비할 때 할 일은 채팅방에, 일정은 캘린더에, 자료는 각자의 북마크에 흩어집니다. MODI는 목표와 기간을 가진 방을 만들어 투두·일정·자료를 한곳에서 관리하고, 모아둔 자료를 근거로 AI가 다음 할 일을 추천해 주는 공동 To-Do 앱입니다. 4인 팀에서 백엔드·인프라·AI를 맡아 App Store 출시까지 갔고, 지금도 서버를 직접 운영하고 있습니다.

시스템 아키텍처

단일 Oracle Cloud ARM 인스턴스 위에 전 구성요소를 Docker Compose로 운영합니다. 외부에 노출된 것은 Caddy 하나뿐이고(HTTPS·TLS 자동 발급), 점선 영역의 PostgreSQL·Redis·MinIO·AI 서버는 호스트 포트 바인딩 없이 내부 네트워크에서만 접근됩니다. 보안그룹을 잘못 열어도 DB가 인터넷에 노출되지 않는 구조입니다. 색상은 담당 영역 기준입니다.

한 일

  • 인프라 설계·구축 — Caddy(TLS 종료)·Spring Boot 두 벌(blue/green)·PostgreSQL·Redis·MinIO·FastAPI AI 서버를 단일 ARM 인스턴스에 Docker Compose로 구성했습니다. TLS 인증서를 쥔 인프라층과 앱층을 분리해, 앱을 재배포해도 엣지가 흔들리지 않게 했습니다.
  • CI/CD와 무중단 배포 — Jenkins 파이프라인(497줄)을 GitHub Actions 한 파일로 이전했습니다. 경로 필터로 바뀐 부분(app/server/ai)만 테스트하고, main push는 테스트를 통과해야 SSH 배포가 돕니다. 배포 스크립트가 대기 색을 띄워 헬스체크한 뒤 Caddy 설정 한 줄을 바꿔 트래픽을 전환하는 blue/green 무중단 배포입니다.
  • AI 서버 개발 — 투두 추천 전용 FastAPI 서버를 만들었습니다. LangGraph 파이프라인으로 자료 선별 → 후보 생성 → 검수 → 의미 중복 제거를 돌리고, 외부 호출은 LLM 1회 + 임베딩 2회로 고정했습니다. 순수 함수와 LLM 호출을 갈라놓아 API 크레딧 없이 로직 전체를 테스트합니다.
  • AI 품질을 측정으로 관리 — 방 단위 평가 러너와 프롬프트 프로브를 만들어 변경마다 실측했습니다. 검수 단계가 판정을 조용히 빠뜨리는 문제를 계수기로 감지하고, 60회 실측으로 후보 번호 매기기(0번 시작 → 1번 시작) 한 줄이 원인임을 좁혀 판정 누락 33%를 0%로 만들었습니다.
  • 백엔드 운영 — 운영 부팅을 깨뜨린 Flyway 마이그레이션 체크섬 사고를 겪고 재발 방지 가드를 넣었고, 로그 로테이션·DB 백업, MinIO presigned URL의 자기 참조 문제(인스턴스가 자기 공인 IP로 못 들어가는 헤어핀)를 Docker 내부 DNS 별칭으로 해결하는 등 서비스가 실제로 계속 돌게 만드는 일을 맡고 있습니다.

AI 추천 파이프라인 — LangGraph

방의 목표와 모아둔 자료를 입력으로, 바로 실행할 수 있는 투두 후보를 만들어 내는 파이프라인입니다. 아래 그래프는 실제 코드의 노드·엣지 구조 그대로입니다(점선은 조건부 분기). 

flowchart TD

  select --> generate(generate)
  generate -.->|후보 0개| DONE([종료])
  generate -.-> batch(batch)
  generate -.-> critique(critique)
  critique -.->|전부 반려 → 빈 목록| DONE
  critique -.-> batch
  critique -.->|재생성 · 운영 기본 off| generate
  batch --> dedupe(dedupe)
  dedupe --> DONE

  class START,DONE endpoint;
노드하는 일외부 호출
select자료를 네 축(좋아요·핀·목표 유사도·최근성)으로 줄 세우고, 프롬프트 예산을 넘는 뒤쪽을 버립니다임베딩 1회
generate후보 생성 + 문자열 필터LLM 1회
critique바로 실행할 수 없는 후보를 반려합니다LLM 1회
batchdedupe가 쓸 임베딩 요청을 묶습니다없음
dedupe이미 보여준 후보와 의미가 겹치는 것을 버립니다임베딩 1회

설계에서 지킨 원칙은 두 가지입니다. 하나, 나쁜 후보를 보여주느니 안 보여준다 — 검수가 전부 반려하면 빈 목록으로 끝냅니다. 둘, 그럴듯한 개선도 측정으로 판단한다 — 반려된 후보를 다시 생성하는 루프를 만들어 실측했지만, 후보 수는 회복되는 대신 지연 상한 10초를 37~40% 깨는 것으로 나와 기각하고 설정으로만 남겼습니다.

결과 & 배운 점

App Store에 실제 출시했고, 출시 후에도 같은 인프라에서 서비스를 계속 운영하고 있습니다. 기술적으로 가장 크게 배운 건 운영은 증상 제거와 기전 이해를 구분해야 한다는 점입니다. 검수 누락 버그는 한 줄로 고쳤지만 "왜 0번 시작일 때만 누락되는가"는 끝내 알 수 없었고, 그래서 고쳤다고 끝내는 대신 재발을 알아챌 계수기를 운영 지표에 남겼습니다. 인프라도 마찬가지로, 포트를 닫은 이유· 층을 나눈 이유 같은 "왜"를 문서로 남겨 두니 사람이 바뀌어도 구조가 무너지지 않았습니다. 만들 때보다 돌아가게 유지할 때 필요한 근육이 따로 있다는 걸, 실제 사용자가 있는 서비스를 운영하며 배우는 중입니다.
