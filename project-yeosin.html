배경 & 문제

은행의 여신 심사를 어떻게 편하게 도울 수 있는지, 그 서비스 흐름 자체를 보여 주는 것이 중요한 프로젝트였습니다. 일반 소비자가 아니라 여신 업무를 맡은 담당자만 쓰는 서비스라서, 많은 트래픽보다 심사 한 건을 끝까지 정확하게 처리하는 쪽에 맞춰 규모를 정했습니다. 팀에서 인프라와 인증 · 감사 로그를 맡았습니다.

시스템 아키텍처

Lightsail 한 대(4 vCPU · 16GB)에 Docker Swarm으로 서비스 11개를 올렸습니다. 밖으로 포트를 여는 것은 Nginx 하나뿐이고(80 · 443), OCR은 Tailscale로 연결한 GPU 노트북에서 처리합니다.

배포 성공 표시 너머의 실제 상태 확인

① 첫 자동 배포가 헬스체크에서 502DNS 다시 묻기
상황backend 컨테이너는 172.18.0.8에 살아 있었지만, Nginx 오류 로그에는 172.18.0.9로 보낸 요청이 남아 있었습니다
원인Nginx는 기동할 때 upstream 이름을 IP로 한 번 바꿔 계속 씁니다. 배포로 새로 뜬 backend는 새 IP를 받습니다
해결resolver 127.0.0.11 valid=10s와 proxy_pass 변수로, 10초가 지난 요청에서 Docker DNS에 다시 묻게 했습니다
② 다음 배포는 성공인데 설정이 그대로디렉터리 마운트로
상황서버 폴더와 컨테이너 안에서 같은 설정 파일의 inode와 크기를 비교하자 서로 달랐습니다 — 서버 1112487 · 2371B, 컨테이너 1088149 · 1694B
원인파일 하나만 바인드 마운트하면 그 순간의 inode에 묶이는데, git은 파일을 지우고 새로 써서 inode가 바뀝니다. 리눅스에서 재현해 서버 inode만 2263971 → 2263952로 바뀌는 것을 확인했습니다
해결설정 디렉터리를 마운트해 컨테이너가 열 때마다 이름으로 찾아가게 했습니다
결과같은 조사에서 로컬 설정 검사가 경로 변환 때문에 빈 폴더를 검사하던 것도 찾아, 서버의 실제 설정으로 검사를 옮겼습니다
여신보좌관 회고

전에는 인프라를 서버를 띄우고 배포하는 일로만 봤습니다. 이번에는 팀원이 CI를 기다리는 시간과, 배포가 정말 성공했는지 확인하는 기준까지 인프라가 책임질 일이라는 걸 배웠습니다.

감사 로그 — 고칠 수 없는 기록

append-only 해시 체인중간 행 수정 · 삭제 검출
상황위변조 방지가 요구사항이었습니다. DB 권한만으로는 DB 관리자를 막지 못하고, 전용 WORM 저장소는 프로토타입에 과하다고 판단해 해시 체인을 골랐습니다
설계각 행이 앞 행의 해시를 담고, 체인 검증이 처음부터 다시 계산해 깨진 첫 행을 찾습니다. 수정할 수 있는 JPA 엔티티는 아예 만들지 않았습니다
함정PostgreSQL JSONB는 키를 다시 정렬하고 공백을 없애며, timestamptz는 마이크로초까지만 저장합니다. 저장된 문자열을 해시하면 다시 읽었을 때 검증이 깨집니다
해결키 정렬 · 공백 없는 JSON을 직접 만드는 규칙을 canon_version 1로 고정하고, 시각은 마이크로초로 잘라 해시했습니다
결과중간 행 UPDATE · DELETE를 테스트에서 검출합니다. 꼬리를 잘라내거나 전체를 다시 계산하면 못 잡는다는 한계도 명세에 적었습니다
동시에 써도 체인이 갈라지지 않게20스레드 → 20행
원인꼬리 읽기 → 해시 계산 → INSERT 사이에 다른 요청이 끼면 같은 앞 행을 가리키는 두 행이 생깁니다
해결pg_advisory_xact_lock으로 인스턴스가 여럿이어도 직렬화하고(트랜잭션이 끝나면 풀림), prev_hash에 UNIQUE를 걸어 잠금을 빠뜨린 코드까지 DB가 막게 했습니다
판단격리 수준은 READ COMMITTED를 유지했습니다. REPEATABLE READ면 잠금을 얻은 뒤에도 옛 꼬리를 읽습니다
결과동시 20스레드 추가 테스트에서 20행이 생기고 체인 검증을 통과합니다
DB 권한 — 트리거 한 겹에서 두 겹으로42501 권한 오류
상황수정 금지 트리거만 있었고 backend가 표 소유자로 접속해, 앱 연결로 DISABLE TRIGGER가 가능했습니다. SQL 인젝션 하나로 트리거를 끄고 기록을 다시 쓸 수 있는 상태였습니다
해결런타임 계정은 audit_log에 SELECT · INSERT만 갖고, 표 변경은 Flyway 소유자 계정만 합니다. 표가 하나뿐인 지금 하는 것이 가장 싸다고 보고 이후 표의 기본 권한도 함께 잡았습니다
결과통합 테스트에서 추가는 성공하고, UPDATE · DELETE · TRUNCATE · 트리거 끄기는 모두 권한 오류(42501)로 거부됩니다
한계프로세스가 탈취되면 같은 컨테이너의 Flyway 소유자 자격 때문에 막지 못한다고 명세에 적어 두었습니다

로그인과 2차 인증

JWT에서 SSAFY 통합인증 + DB 세션으로결정 번복
상황처음에는 무상태라 여러 인스턴스에 유리하다는 이유로 JWT를 골랐습니다
판단SSAFY 계정으로 로그인하면 회원가입 · 비밀번호 재설정 흐름이 필요 없고, 서버가 Lightsail 한 대라 무상태의 이득이 없으며, JWT는 이미 발급한 토큰을 바로 무효화할 수 없어 DB 세션으로 바꿨습니다
구현응답이 표준과 달라도 실패 원인이 보이도록 Spring OAuth2 Client 대신 직접 구현했습니다. 실제로 호출해 보니 인가 코드 파라미터는 문서의 Code가 아니라 code였고, 토큰 응답은 snake_case였습니다
결과state 불일치 거절과 콜백 재생 방지를 포함한 통합 테스트 7개
TOTP 2차 인증을 라이브러리 없이RFC 6238 벡터 6개
판단후보 라이브러리는 5년째 갱신이 없고 다른 의존성을 함께 끌고 와, JDK HmacSHA1과 이미 쓰던 commons-codec(Base32)로 직접 구현했습니다
검증RFC 6238 부록 B 시험 벡터 6개로 확인하고, 코드 비교는 상수 시간 비교(MessageDigest.isEqual), 같은 6자리 재사용은 거절합니다
문제인증 실패 감사 기록이 예외 롤백에 같이 지워져, 실패한 사람만 흔적이 남지 않았습니다
해결통합 테스트가 이를 잡았고, 실패 기록만 별도 트랜잭션(REQUIRES_NEW)으로 분리했습니다
